# A+B 功能改造方案

> 版本：v1.0（已实施）
> 日期：2026-11-06
> 范围：A 创作闭环 + B 后期与一致性
> 不含：C 接入扩展（ComfyUI、厂商预设、一键接入）与 D 工作室化（项目、画布、分镜、时间线、Agent、多用户）

---

## 0. 结论与边界

### 0.1 这份文档解决什么

OneFrame 已经完成“多供应商统一调度”这一层：渠道、密钥池、厂商 × 模型、任务轮询、失败可解释、费用记录。当前缺的是三个上游项目里最显眼的**创作工作流**。本次改造把这条链路补齐：

```
参考素材 → 组合/提取/随机 → 生成 → 对比/复用 → 局部编辑/精修/拆分 → 版本归档
```

### 0.2 设计原则（不改变）

1. **本地优先**：SQLite + 本地文件；参考素材只索引，不搬运。
2. **一个模型 = 一个厂商 + 一个上游模型名**：不做跨厂商兜底。
3. **失败即失败**：401/403/429 只冷却 Key，当次任务不重发。
4. **工具复用任务管线**：提取、精修、局部重绘、角色一致性都走现有 `jobs` 表与 `JobRunner`，不另建执行器。
5. **服务端持有工具提示词**：固定模板在 `core/tools.py`，用户只能补充自由描述，不能改隐藏核心指令。
6. **能力先校验**：模型不支持参考图/局部重绘时，界面不展示入口，接口直接拒绝。
7. **不做隐藏状态**：提示词增强、参考拼图都返回可编辑文本/可下载文件。
8. **版权边界**：参考素材仍然只索引用户本机文件；远程热链素材默认不下载、不缓存。

### 0.3 变更前准备

当前目录**不是 git 仓库**。开始改造前必须做一次可回滚基线：

```bash
cd D:\0Z\api2img
git init
git add -A
git commit -m "baseline before A+B"
```

同时复制一份运行时数据（数据库 + 密钥必须成对）：

```powershell
Copy-Item data\oneframe.db data\oneframe.db.v5.bak
Copy-Item data\secret.key data\secret.key.bak
```

改造期间用开发模式验证：

```bash
cd frontend && npm run dev
.venv\Scripts\python.exe backend\run.py
```

## 3. 数据模型与迁移

### 3.1 schema v6

一次迁移完成 A/B 所需字段，`app_meta.schema_version = '6'`。

```sql
-- 参考库：分组、视角、深度图伴生文件
ALTER TABLE library_items ADD COLUMN group_key TEXT NOT NULL DEFAULT '';
ALTER TABLE library_items ADD COLUMN variant_label TEXT NOT NULL DEFAULT '';
ALTER TABLE library_items ADD COLUMN depth_path TEXT;
ALTER TABLE library_items ADD COLUMN depth_thumb_path TEXT;
ALTER TABLE library_items ADD COLUMN has_depth INTEGER NOT NULL DEFAULT 0;

CREATE INDEX IF NOT EXISTS idx_library_group ON library_items(group_key);
CREATE INDEX IF NOT EXISTS idx_library_depth ON library_items(has_depth, kind);

-- 作品：派生关系与版本
ALTER TABLE assets ADD COLUMN parent_id TEXT;
ALTER TABLE assets ADD COLUMN root_id TEXT;
ALTER TABLE assets ADD COLUMN tool TEXT NOT NULL DEFAULT '';
ALTER TABLE assets ADD COLUMN version INTEGER NOT NULL DEFAULT 1;

CREATE INDEX IF NOT EXISTS idx_assets_root ON assets(root_id, version);
CREATE INDEX IF NOT EXISTS idx_assets_parent ON assets(parent_id);

-- 提示词库
CREATE TABLE IF NOT EXISTS prompts (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  category TEXT NOT NULL DEFAULT 'custom',
  text TEXT NOT NULL,
  negative TEXT NOT NULL DEFAULT '',
  tags TEXT NOT NULL DEFAULT '',
  favorite INTEGER NOT NULL DEFAULT 0,
  builtin INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_prompts_category ON prompts(category, favorite, created_at DESC);
```

### 3.2 迁移步骤（`db._migrate_v6`）

1. **自动备份**：迁移前用 `sqlite3.Connection.backup` 写 `oneframe.db.v5.bak`；只写一次，已存在则跳过。
2. 执行上述 DDL。
3. 回填现有 4,345 条参考库：
   - `pose`：`group_key = 'pose:' + 体系 + ':' + 编号`（编号在不同体系会复用，不能只用编号）；没有编号时退回 `external_id`。`variant_label = meta.angle`。
   - `costume` / `portrait`：`group_key = external_id`，`variant_label = ''`。
   - `has_depth`：按 `source` 里的仓库根目录检查 `img/depth/{pose_id}.webp` 是否存在；存在则写 `depth_path` / `depth_thumb_path`。
4. 回填现有 44 件作品：`root_id = id`、`version = 1`。
5. 现有 `assets.meta` 不强制补 `refs`；读取时回退到 `jobs.request.refs`。
6. 写入 `schema_version = 6`。

> 迁移只改索引与元数据，不移动、不复制任何参考图片。

### 3.3 分类规则

- `taxonomy.FIELDS["costume"]` 增加可选维度 `("视角", 3)`，只对 Shisei 这类有 `views` 的记录写入；普通服装没有该 facet 时不显示。
- `TAXONOMY_VERSION` 从 `6` 升到 `7`，启动时 `ensure_taxonomy` 会自动重建一次。
- 深度图不作为独立条目，也不新增 facet；它是姿势条目的伴生文件，用 `has_depth` 标记。

## 4. A 阶段详细设计

### A1 参考库导入器升级 + 深度图 + 多视角

#### A1.1 目标

1. 现有 4,345 条不重复、不丢失。
2. 新增 Shisei 227 个本地视角。
3. 为 1,439 条姿势补深度图路径。
4. 参考库/选图器支持“白模 ↔ 深度图”切换和同组多视角切换。
5. 远程热链的 1,760 条默认跳过，并在导入结果里明确报告。

> 前置：先把本机 `ai-pose-gallery-zh` 更新到最新（`git pull`），否则没有 `costume-shisei-zh.json`、`img/depth/` 和新增字段。

#### A1.2 导入逻辑

`core/library.py`：

```python
GALLERY_FILES = (
    ("pose", "pose-zh.json"),
    ("costume", "costume-zh.json"),
    ("portrait", "portrait-zh.json"),
    ("costume", "costume-shisei-zh.json"),   # 新增
)
```

- 普通文件：保持现有逻辑。
- `costume-shisei-zh.json`：
  - `views` 是字符串形式的 JSON 数组，解析后每个 view 生成一条 `library_items`。
  - `external_id = f"costume-view:{entry['id']}:{view['id']}"`。
  - `group_key = f"shisei:{entry['id']}"`。
  - `variant_label = view['label']`（正面/斜侧/侧面/背面）。
  - 标题：`f"{entry['服装名称']} · {view['label']}"`。
  - 图片路径必须存在且在允许目录内，否则计入 `skipped_missing`。
- 深度图：
  - 对每条 pose：
    - `depth_path = root/img/depth/{pose_id}.webp`
    - `depth_thumb_path = root/thumbs/depth/{pose_id}.webp`
  - 两者都存在才 `has_depth=1`；只存在原图也允许（缩略图缺失时回退原图）。
- 远程记录：
  - `原图` 以 `http://` / `https://` 开头时跳过，计入 `skipped_remote`。
  - 不自动下载。
  - `costume-gia-anime-zh.json` / `costume-anime-zh.json` 只读取用于统计 `skipped_remote`，不写入索引。
- 路径解析：
  - `source` 形如 `pose-gallery:D:\0Z\ai-pose-gallery-zh`；取根目录必须用 `source.removeprefix("pose-gallery:")`，不能按冒号 `split`（Windows 盘符本身含冒号）。
- 返回值扩展：

```json
{
  "added": 227,
  "updated": 1439,
  "scanned": 1439,
  "skipped_remote": 1760,
  "skipped_missing": 0,
  "depth_added": 1439,
  "sources": {"pose": 1439, "costume": 1634, "portrait": 1499}
}
```

**同组视角**

### A2 对比工作台

#### A2.1 目标

两种对比工作流，共用一个对比引擎：

1. **结果 vs 参考**：验证生成是否遵循参考图的人物、服装、姿势；默认叠加，方便看贴合度。
2. **作品 vs 作品**：比较两次生成结果（不同模型、不同版本、不同提示词）；默认并排，方便看差异。

两种都支持：
- 双列并排；
- 叠加滑杆；
- 手动缩放/拖动对齐；
- 键盘 `←` / `→` / `Home` / `End` 控制滑杆。

#### A2.2 数据来源

生成完成时，在 `assets.meta.refs` 写入参考快照：

```json
{
  "refs": [
    {"role": "character", "name": "人像01", "source": "library", "id": "...", "variant": "base"},
    {"role": "costume", "name": "服装02", "source": "asset", "id": "...", "variant": "base"}
  ]
}
```

新增接口：

```
GET /api/assets/{id}/refs
```

```json
{
  "items": [
    {
      "role": "character",
      "name": "人像01",
      "source": "library",
      "id": "...",
      "variant": "base",
      "url": "/api/library/.../file",
      "thumb_url": "/api/library/.../file?size=thumb"
    }
  ]
}
```

- 优先读 `assets.meta.refs`；没有则回退 `jobs.request.refs`。
- 文件已删除时返回 `missing: true`，前端显示占位。

#### A2.3 前端 `CompareModal`

一个弹窗，两种入口，不写两套对比 UI。

```ts
type CompareMode = "fidelity" | "selection";

type CompareSource = {
  url: string;
  label: string;
  kind: "generated" | "reference" | "asset";
  width?: number;
  height?: number;
};
```

- **`fidelity`（结果 vs 参考）**
  - 左：当前生成结果；右：它的参考图。
  - 默认 `overlay`；多张参考时顶部用 chips 选择“人物 / 服装 / 姿势”。
  - 右侧标签显示角色：`参考 · 姿势构图`。
  - 入口：Gallery 灯箱、Studio 结果灯箱的“对比参考”。
- **`selection`（作品 vs 作品）**
  - 左 A、右 B，都是作品。
  - 默认 `side`；叠加仍可用（适合同提示词/同构图的版本对比）。
  - 选图方式：灯箱里点“设为对比 A”，再去另一张点“与 A 对比”；或在作品卡片上点“对比”进入对比篮（最多 2 张），选满自动打开弹窗。
  - 右侧标签显示 `作品 A / 作品 B`，可一键交换左右。
  - 入口：Gallery 卡片、Gallery 灯箱、Studio 结果灯箱。
- **共用交互**
  - 叠加：两张图绝对定位；上层用 `clip-path: inset(0 calc(100% - var(--pos)) 0 0)`；滑杆 + 键盘控制。
  - 对齐：两张图各自维护 `{scale, x, y}`；滚轮缩放、拖拽平移；“重置对齐”回到 `scale=1,x=0,y=0`。
  - 不做自动 CV 对齐，避免引入额外模型。
  - 尺寸不同：各自 fit 到舞台，独立缩放/平移；并排模式显示尺寸提示，叠加模式提示“比例不同，叠加只作构图参考”。
  - 视频 v1 不参与对比，只对比图像；视频并排播放后续再做。
- 无后端变更（除 refs 接口）。

#### A2.4 验收

- **结果 vs 参考**：任一有参考图的结果可以打开对比；左右图正确；多参考可切换。
- **作品 vs 作品**：任选两张作品可以并排/叠加；左右可交换。
- 叠加滑杆可键盘控制；对齐后两张图不跳变。
- 尺寸不同的两张图不会拉伸变形。
- 参考文件被删除时显示“参考已丢失”，不崩溃。
- 旧作品（没有 `meta.refs`）通过 job 回退也能对比。

## 5. B 阶段详细设计

### B1 局部重绘（蒙版）

#### B1.1 数据链路

1. 前端在源图上涂抹，导出透明底 PNG 蒙版（编辑区域 alpha=0，保留区域 alpha=255）。
2. 提交 `POST /api/generate`：

```json
{
  "model_id": "...",
  "prompt": "把衣服换成红色针织开衫",
  "tool": "inpaint",
  "options": {"source_asset_id": "..."},
  "mask": "data:image/png;base64,...",
  "refs": [{"asset_id": "...", "role": "reference"}],
  "count": 1,
  "params": {"aspect_ratio": "1:1", "resolution": "1K"}
}
```

3. 后端：
   - 解码 data URL，校验 PNG、尺寸与源图一致、≤ 8 MB；
   - 保存到 `data/uploads/masks/{job_id}.png`；
   - job snapshot 写 `mask_path`；
   - worker 读取为 `RefImage(name="mask", mime="image/png", role="mask")`。
4. 适配器：
   - `Adapter.supports_mask` 默认 `False`；
   - `OpenAIImagesAdapter.supports_mask = True`；
   - `/images/edits` multipart 增加 `mask` 文件字段；
   - 其他适配器不支持时，`validate()` 抛 `Unsupported("当前协议不支持局部重绘")`。
5. 源图与蒙版必须同尺寸：
   - 源图按最长边 2048 等比缩放并转 JPEG(92)；
   - 蒙版用**同一目标尺寸**、`Image.NEAREST` 缩放，保留 alpha；
   - 两者成对生成，禁止只缩放其中一个；
   - 尺寸不一致时接口直接拒绝，不把问题留给上游。
5. 能力校验：
   - 模型 `caps.features` 必须包含 `"inpaint"`；
   - 模型编辑器增加“局部重绘”复选框；
   - 只有 `inpaint` 能力 + `supports_mask` 的模型出现在重绘弹窗。

#### B1.2 前端 `InpaintModal`

- 画布：
  - 底图 + 半透明红色蒙版层；
  - 工具：画笔、橡皮、笔刷大小、撤销、清空；
  - 支持滚轮缩放、拖拽平移（与对比弹窗共用逻辑）。
- 导出：
  - 使用离屏 canvas 生成同尺寸蒙版 PNG；
  - 编辑区域透明，其余不透明；
  - 提交前预览蒙版。
- 表单：
  - 重绘提示词；
  - 模型选择（只列支持 inpaint 的可用模型）；
  - 费用预估。
- 结果：
  - 与原图并排/叠加对比；
  - “继续重绘”“精修”“存入参考库”。

#### B1.3 验收

- OpenAI 兼容模型可完成一次局部重绘。
- 蒙版尺寸与源图不一致时接口拒绝。
- 不支持 inpaint 的模型不显示入口。
- 结果资产 `parent_id` 指向源图，版本 +1。

### B3 宫格拆分

#### B3.1 接口

```
POST /api/assets/{id}/split
{"rows": 2, "columns": 2, "cells": [0,1,2,3]}
```

- `rows` / `columns`：1–4；`cells` 可省略表示全部。
- 输入限制：≤ 40 MP、最长边 ≤ 8192。
- 用整数边界切分，保证不重叠、不丢像素：

```python
left = col * width // columns
right = (col + 1) * width // columns
top = row * height // rows
bottom = (row + 1) * height // rows
```

- 每个 cell：
  - `storage.save_output` 保存 PNG；
  - `origin="split"`；
  - `meta.grid = {rows, columns, row, col, index}`；
  - `parent_id` = 源图；`root_id` = 自身 id；`version` = 1（见 B7 血缘规则）。
- 返回 `{"items": [Asset, ...]}`。
- 同步操作；用 `asyncio.to_thread` 避免阻塞事件循环。

#### B3.2 前端 `GridSplitModal`

- 入口：Gallery 灯箱、Studio 结果灯箱（仅图像）。
- 网格选择：2×2、3×3、4×4 或自定义行列。
- 预览：在图上叠加网格线；点击 cell 选中/取消。
- 拆分后：
  - 展示结果缩略图；
  - “全部加入参考库”“下载全部（ZIP 可选）”。
- 拆分不产生新的生成任务，不计费。

#### B3.3 验收

- 2×2 拆分得到 4 张，尺寸之和覆盖原图。
- 奇数尺寸不丢像素、不重叠。
- 只拆分选中的 cell。

### B7 素材版本

#### B7.1 血缘规则

- 根资产：`root_id = id`、`version = 1`。
- 版本派生（提取 / 重绘 / 精修 / 角色 / 放大）：
  - `parent_id` = 直接来源；
  - `root_id` = 来源的 `root_id` 或来源 `id`；
  - `version` = 同 root 下最大值 + 1；
  - `tool` = `extract_costume` / `inpaint` / `refine` / `character` / `upscale`。
- 拆分派生（split）：
  - `parent_id` = 源图；
  - `root_id` = 自身 id；
  - `version` = 1；
  - 每个 cell 是新素材线，不与源图并列成“版本”。
- 生成任务如果 `options.source_asset_id` 存在，也按版本派生处理；否则为根。

#### B7.2 接口

```
GET /api/assets/{id}/versions
```

```json
{
  "root_id": "...",
  "current_id": "...",
  "items": [
    {"id": "...", "version": 1, "tool": "", "thumb_url": "...", "created_at": "..."},
    {"id": "...", "version": 2, "tool": "inpaint", "thumb_url": "...", "created_at": "..."}
  ]
}
```

- 按 `version` 升序。
- 删除中间版本不影响其他版本；根被删除时，剩余版本仍可通过 `root_id` 聚合（允许悬空）。

#### B7.3 前端 `VersionStrip`

- 位置：Gallery / Studio 灯箱底部。
- 展示：
  - 横向缩略图；
  - 当前版本高亮；
  - 标签：原图 / 局部重绘 / 精修 / 拆分 / 放大；
  - 点击切换大图；
  - “与当前对比”打开 `CompareModal`。
- 只显示同 root 的版本；单版本时隐藏。

#### B7.4 验收

- 对一张图做局部重绘，原图与结果在同一版本条。
- 拆分产生的每个 cell 各自成为新 root，版本条只显示 cell 自身。
- 删除根后，版本条仍能展示剩余项。

> 设计取舍：拆分产生的多个 cell **不共享同一个 root 作为并列版本**，而是每个 cell 以源图为 `parent_id`、以自己的 id 为 `root_id`（各自是一条新素材线）。这样版本条不会把 4 个不同内容误认为“同一张图的 4 个版本”。如果需要“源图的所有派生”，另加 `parent_id` 查询视图。

## 7. 后端实现要点

### 7.1 `core/tools.py`

```python
TOOL_MODES = {"extract_costume", "refine", "inpaint", "character"}

def build_prompt(tool: str, options: dict, user_prompt: str, refs: list) -> str: ...
def validate_tool(tool: str, options: dict, model: dict, adapter) -> None: ...
def tool_meta(tool: str, options: dict) -> dict: ...
```

- 所有固定提示词集中在此文件；
- `validate_tool` 检查能力、参考图数量、mask、源资产；
- 不读写数据库，便于单测。

### 7.2 `api/generate.py`

处理顺序：

1. 校验模型与 `tool`；
2. 若 `tool` 非空：
   - 解析 `options.source_asset_id`；
   - 把源资产加入 refs（如果前端没传）；
   - `build_prompt` 覆盖/拼接 prompt；
   - `validate_tool`。
3. 若 `mask`：
   - 解码、校验 PNG 与尺寸；
   - 保存 `uploads/masks/{job_id}.png`；
   - snapshot 写 `mask_path`。
4. `routing.check`；
5. 写 job snapshot：`tool/options/mask_path/matrix_id/refs`；
6. 返回。

### 7.3 `core/worker.py`

- `_resolve_refs` 增加 `variant`：
  - `library_id` + `variant="depth"` → `library_items.depth_path`；
  - 不存在时回退 base，并在 `attempts` 记录。
- 新增 `_load_mask(conn, job)`：
  - 读取 `mask_path`；
  - 校验存在且在 `data/` 下；
  - 返回 `RefImage`。
- `_finish`：
  - 写 `assets.meta.refs` 快照；
  - 写 `tool`、`parent_id`、`root_id`、`version`；
  - 写 `source_asset_id`/`character_mode` 等工具元数据。
- 工具失败仍按现有失败类型处理；不自动换模型。

### 7.4 `providers/base.py`

```python
@dataclass
class GenRequest:
    ...
    mask: RefImage | None = None

class Adapter:
    supports_mask: bool = False
    def validate(self, req):
        ...
        if req.mask and not self.supports_mask:
            raise Unsupported("当前协议不支持局部重绘")
```

### 7.5 `providers/openai_images.py`

- `supports_mask = True`。
- `/images/edits` multipart：

```python
if req.mask and req.mask.data:
    files.append(("mask", ("mask.png", req.mask.data, "image/png")))
```

- 注意：OpenAI 要求 mask 与 image 尺寸一致；`validate` 中已校验。
- 只支持 `n=1` 的局部重绘（多张时 `n` 可能导致部分中转不支持；v1 固定 1）。

### 7.6 `core/storage.py`

新增：

```python
def save_mask(data: bytes, job_id: str) -> str: ...
def split_image(source: Path, rows: int, columns: int, cells: list[int]) -> list[bytes]: ...
def upscale_image(source: Path, factor: int) -> dict: ...
def build_zip(entries: list[tuple[str, Path]]) -> bytes: ...
```

- `save_mask`：写入 `uploads/masks/`，返回相对路径。
- `split_image`：PIL 裁剪，返回 bytes 列表。
- `upscale_image`：LANCZOS，返回 bytes + 尺寸。
- `build_zip`：内存 ZIP，名称去重。

### 7.7 安全

- URL 导入：SSRF 防护见 A6。
- ZIP：只打包允许目录内文件；文件名 sanitize。
- mask：只接受 PNG 文件头；大小上限。
- split/upscale：尺寸上限，避免内存炸弹。
- 所有新接口沿用 `127.0.0.1` 无鉴权边界；公网部署仍需反代鉴权。

## 11. 风险与取舍

| 风险/取舍 | 说明 | 应对 |
| --- | --- | --- |
| 远程素材不可索引 | 动漫/CharaDB 1,760 条是热链，仓库不存图 | 默认跳过并报告；用户自行下载后按文件夹导入；远程缓存另立项目 |
| 深度图版权 | 深度图与姿势图同源 | 只索引本地副本，不打包、不再分发 |
| 随机搭配性别不一致 | 当前数据无统一 gender facet | v1 不做性别约束；后续补 facet |
| 局部重绘供应商有限 | 仅 OpenAI 兼容 `/images/edits` 支持 mask | 能力门控；不支持时不显示入口 |
| 对比无自动对齐 | 不做 CV 对齐 | 手动缩放/拖动；后续可接图像配准 |
| 提示词增强不是 AI | 本地规则，表达力有限 | 明确标注；后续接文本模型再升级 |
| 本地放大不是 AI 超分 | LANCZOS 只提升分辨率 | 明确标注；后续接超分模型 |
| 角色一致性受模型影响 | 不同模型遵循度不同 | 预设提示词 + 参考图；结果可版本化重试 |
| SQLite 单机 | 新功能增加表与索引 | 仍为单用户；迁移前备份；避免长事务 |
| Studio 单文件过大 | 1,569 行继续加会难维护 | 先拆 `components/studio/`，再接入新 UI |
| 无 git 仓库 | 无法回滚 | 先 `git init` + baseline commit + 数据备份 |
| ZIP 内存占用 | 大参考图打包 | 20 文件 / 100 MB 上限；超限 413 |

## 17. 长期路线（D1 → D2 → D3）

已确认的最终目标是 **D3**：把 OneFrame 从“统一生成工作台”逐步长成 inspiration 风格的 AI 影视/短片创作平台。不一次性照搬，按下面三档递增。

### D1 生成增强（轻量，约 1–2 周）

- LLM 提示词改写（接入文本/对话模型，作为本地规则增强的升级）
- 厂商预设与一键接入（C 范围：阿里百炼、火山方舟、ComfyUI 等）
- 视频裁剪 / 抽帧 / 封面
- 素材采纳与引用（把生成结果带入下一次创作，保留来源关系）

### D2 素材与项目（中等，约 3–4 周）

- 项目 / 作品集：把素材、任务、版本组织到项目下
- 素材不可变版本、引用关系、素材库文件夹与封面
- 音频 / 字幕 / 转写
- 简单多用户与权限；需要评估 SQLite 边界，可能引入轻量任务队列
- 这一步开始出现“从单图生成走向持续创作”的形态

### D3 影视工作室（重，约 1–2 个月+）

- 自由画布：节点图、连线、绘图裁切、依赖执行、离线打包
- 故事 / 剧本：小说导入、章节、场次、Fountain 导出
- 分镜 / 导演台：镜头、画面版本、机位、关键帧、运镜
- 时间线剪辑：多画面轨、音轨、字幕轨、预览/导出、历史恢复
- Agent / 技能包 / MCP 网关
- 官网 / 博客、完整多用户与权限
- 架构升级：Postgres/pgvector、Redis/Celery、MinIO、鉴权

### 推进原则

1. 每档都必须能独立使用，不出现“半成品平台”。
2. D1 不改变现有 SQLite 单进程架构；D2 先评估数据边界；D3 才做存储与任务架构升级。
3. 每次新需求先判断落在哪一档，再决定是否需要改架构，避免用 D3 的方式解决 D1 的问题。
4. 参考 inspiration 的模块划分与数据模型，但不照搬其部署复杂度。
