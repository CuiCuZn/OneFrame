# 三个项目的分析与整合方案

> 分析对象：
> 1. [anhao/ai-pose-gallery-zh](https://github.com/anhao/ai-pose-gallery-zh)（约 5.3k stars）
> 2. [hongye007/open-pose-costume](https://github.com/hongye007/open-pose-costume)（约 170 stars）
> 3. [Coinsi/inspiration](https://github.com/Coinsi/inspiration)

结论先行：**这三个项目不是竞品，而是同一条链路的三段**——前两个解决"参考素材长什么样"，第三个解决"素材如何进入创作流程"。真正的缺口在中间：**把不同供应商的 Key 统一成一套可核算的生成能力**。OneFrame 就是补这一段，并把三段接起来。

> **设计修订（2026-11-02）**：最初借鉴 inspiration 做了"一个模型挂多条线路、按优先级/权重自动切换"。这与实际使用方式不符：A 厂的 a 模型和 C 厂的 a 模型应当是两个独立选项，选中谁就只走谁，失败就是失败。最终实现改为 **模型 = 厂商 × 上游模型名**，删除跨厂商兜底；仅保留同渠道 Key 在 401/403/429 后的冷却与下次任务换用，单次任务不重试。下文对 inspiration 的分析保留原样（那是它的实现），但第 3 节之后的整合结论以修订版为准。

---

## 一、三个项目分别是什么

### 1. ai-pose-gallery-zh —— 参考素材的"字典"

- **定位**：中文版姿势/服装/人像参考图库，1,439 组姿势 / 2,878 张图，纯静态站 + Cloudflare Workers 代理。
- **核心能力**：三库浏览、姿势五视角切换（白模 ↔ 深度图）、12 种画风、`/studio` 三槽合成（人像 + 服装 + 姿势）、5 家协议直连出图、ComfyUI 4 节点插件。
- **技术**：React 19 + TanStack Router/Query + Tailwind 4 + shadcn；`src/services/aiGenerator.ts`（68 KB）承担全部协议、拼图与 ComfyUI 流程；`functions/api/proxy.ts` 做同源白名单代理。
- **最值得抄的三件事**：
  1. `buildRecipePrompt()`：按"图1/图2/图3"显式指代参考图，逐段声明"只取什么、不复制什么"，结尾压"单画面单人物单视角、不要文字水印"。这是多图参考不崩的关键。
  2. `functions/api/proxy.ts`：Origin 白名单 + 泛域名 + 10 MiB 流式限流 + 只透传 4 个头 + 目标地址走 `x-target-url` 头。
  3. `extractUniversalImage()` 与 `PROVIDER_META` 表驱动：一份函数吃掉 `b64_json` / `url` / Responses 等返回形态，新增供应商只加一行配置。
- **不能直接用的部分**：图片与 `data/` 明确排除在 MIT 之外，且是"未获正式授权的镜像存档"；NSFW 只在前端开关；筛选状态不进 URL；单文件 68 KB 无测试。

### 2. open-pose-costume —— 参考素材的"工作台"

- **定位**：中英双语 Reference Studio，把姿势/服饰/人物聚合成"选参考 → 拼 prompt → 出图 → 对照归档"的一条工作流；5,855 张参考，含 42 套自建服饰。
- **核心能力**：三槽组合（姿势 + 服饰 + 可选人物）、服饰提取、结果对照（双列/叠加滑杆）、IndexedDB 历史、打包下载参考图。
- **技术**：React 19 + Vite 7，仅 4 个运行时依赖（react、react-dom、lucide-react、fflate），90 KB 手写 CSS；构建期用 `scripts/build-data.mjs` 强校验翻译/ID/URL。
- **最值得抄的三件事**：
  1. **角色限定式 prompt 模板**：不仅说"参考图2"，还说"只提取可见服饰、鞋履及配饰的款式、颜色、材质与穿戴方式；不复制陈列布局或隐形人台外观"。
  2. **三层图片策略**：`originals/`（生成用）→ `images/`（预览）→ `thumbnails/`（列表），配路径白名单 `isCustomAsset()`。
  3. **构建期数据校验**：缺翻译、重复 ID、URL 非同源直接让 CI 失败，把数据质量挡在构建阶段。
- **不能直接用的部分**：素材授权"不转授下游"；无视频、无任务轮询（同步 180s 单图）；`catalog.json` 5.1 MB 全量加载；无 E2E；无内容审核。

### 3. inspiration —— 完整的 AI 影视创作平台

- **定位**：面向短片/动漫/AI 影视的 Web 工作台，覆盖故事、剧本、素材、画布、分镜、剪辑、Agent 与模型渠道。React + FastAPI + PostgreSQL/pgvector + Redis/Celery + MinIO。
- **核心能力**：项目管理、素材版本与引用、自由画布、分镜/导演台、时间线剪辑、Agent 工具调用、技能包、官网博客、多用户权限。
- **模型层设计（最成熟的部分）**：
  - `adapters/contracts.py` 定义 `Capabilities`（媒体类型、特征、参考图上限、参数 schema、传输方式）与 `submit/poll` 生命周期；
  - 渠道（地址 + 密钥）与模型 profile 分离，创作模型再聚合多个 profile 作为线路；
  - `model_catalog.plan()` 按能力、参数、参考图数量过滤线路，按 `priority` 分组、组内按 `weight` 加权随机；
  - `model_routing.RoutedProvider` 持久化 `routing_state`，**只有上游明确拒绝才切换线路**；提交结果不明的网络错误标记 `submission_unknown` 并停止自动重发，避免重复扣费；
  - 价格按 `per_request / per_second / unconfigured` 建模，预留最高价、成功后按实际线路结算。
- **不能直接用的部分**：部署重（Postgres + Redis + MinIO + Celery），面向多用户与影视长流程，单机个人使用时 90% 的功能用不上；仓库 2 GB+，前端 30+ 页面。

## 三、整合思路：四层架构

```
┌─────────────────────────────────────────────────────────┐
│ 创作层  Studio     提示词 / 参考槽位 / 参数 / 批量 / 视频  │
├─────────────────────────────────────────────────────────┤
│ 资产层  Library    本地索引（姿势/服装/人像/上传）         │
│         Gallery    作品、收藏、复用、下载                  │
├─────────────────────────────────────────────────────────┤
│ 调度层  Router     能力校验 → 厂商/模型绑定 → 密钥池 → 计费 │
│         Worker     提交 → 轮询 → 下载 → 缩略图 → 落库      │
├─────────────────────────────────────────────────────────┤
│ 接入层  Adapters   openai_image / openai_video /          │
│                    gemini_image / gemini_video / generic  │
└─────────────────────────────────────────────────────────┘
```

### 从三个项目各拿什么

**从 ai-pose-gallery-zh**
- 提示词编译器的"图 N 指代 + 只取/不复制 + 单画面收尾"结构（重写为服务端 `core/prompt.py`）。
- 表驱动的供应商元数据（`PROVIDER_DOCS` + 适配器自描述 `param_keys/about`），新增协议只加一个类。
- 通用响应提取思路：`data[] / images[] / output[]` 里同时兼容 `b64_json` 与 `url`，下载失败可回退。
- ComfyUI / 深度图思路留作后续（当前不引入 ComfyUI 依赖）。

**从 open-pose-costume**
- 角色限定式提示词（人物/服装/姿势/风格四类 slot，各自"只取…不复制…"）。
- 三层图片策略的简化版：原图按需读、列表用缩略图、视频抽封面。
- 构建期/导入期校验：导入时检查文件存在、路径必须在允许目录内、按 `external_id` 去重。

**从 inspiration**
- `Capabilities` 契约：媒体类型、feature 集合、参考图上限、参数枚举，提交前本地校验。
- 渠道与模型分离、密钥加密、`attempts` 记录可追溯；但**没有采用**它的多线路聚合与 `priority`/`weight` 调度。
- **"不确定就不重发"**：网络超时导致提交结果未知时，任务标记 `uncertain` 并保留上游任务号，绝不自动换渠道重做。
- 密钥加密存储（Fernet）与"只回传掩码"。
- 价格模型：per_image / per_request / per_second，预留最高价。

### 刻意不做的部分

| 不做 | 原因 |
| --- | --- |
| 跨厂商自动兜底 | 会让「选 A 厂 a 模型」变成不确定的 B/C 厂结果，计费与质量都不可控 |
| 内置 4,000+ 参考图 | 素材授权明确禁止再分发；改为"索引你本机已有的副本" |
| Postgres / Redis / MinIO | 单用户本地工具，SQLite + 本地文件足够，零运维 |
| 多用户/项目权限 | 与"个人创作台"定位冲突，保留后续扩展空间 |
| 完整时间线/分镜/Agent | inspiration 已做得很好；OneFrame 先做"生成"这一段，避免半成品 |
| ComfyUI 节点 | 需要本地 GPU 与工作流语义，先通过"自定义 JSON 接口"兼容其 HTTP API |

## 四、关键设计决策

1. **模型 = 厂商 × 模型**：A 厂的 a 模型与 C 厂的 a 模型是两个选项，各建一条记录；下拉里出现几个，就是几个可独立选择的目标。
2. **失败即失败**：不做跨厂商、跨模型兜底；5xx、超时、内容拒绝都不重试。
3. **密钥属于渠道**：同一渠道的多个 key 用于分摊任务；401/403/429 时该 key 冷却（401 15 分钟、429 2 分钟），当次任务失败，下一次任务换用其他 key。
4. **能力先校验，再下单**：参考图超限、画幅/清晰度不支持、视频数量 >1 在本地直接拒绝，不浪费一次付费请求。
5. **提示词编译放服务端**：同一套编排逻辑既服务界面，也服务 API 调用；前端只负责收集角色与素材。
6. **素材只索引不搬运**：参考库记录绝对路径 + 生成缩略图；删除索引不影响原文件，也不会把第三方图片复制进数据目录。
7. **失败可解释**：每个任务保留 `attempts`（哪个渠道、哪个 key、什么错误、什么阶段），界面能直接看到"为什么失败"。

## 五、后续路线

- **v1.1**：批量矩阵（同一提示词 × 多模型对比）、任务队列公平性、失败任务一键重试（仍不换厂商）。
- **v1.2**：ComfyUI 本地渠道、LoRA/ControlNet 参数、参考图深度图模式。
- **v1.3**：提示词库与团队共享、作品集导出（PDF/网页）、简单协作（局域网多用户）。
- **v2.0**：分镜/时间线（借鉴 inspiration 的镜头与素材版本模型），把"一次生成"升级为"一支短片"。
